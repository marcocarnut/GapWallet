# E1: the end-to-end test plan

The wallet and the signer have only met under Node so far: `tests/` signs with
the signer's library, not the signer app. E1 runs the real thing: GapWallet on
a real network, the signer in zerogap's simulator and then on the rig, and only
QR codes between them (`docs/plans/BITCOIN.md`, "End to end"). E2 repeats it
with Electrum.

## What must be true first

| Needs | For | State |
| --- | --- | --- |
| S2: the signer reads and shows BBQr | series in both directions | done (zerogap 8cbf6eb) |
| Coins on signet, on a key made for this | anything that broadcasts | done: five coins, `tests/e1/RESULTS.md` |
| A go-ahead for each broadcast | a transaction leaving this machine | ask, even on signet |

Parts 1 and 2 need none of these.

## The test wallet

- A new seed made for E1 with the dice39 app, 12 words, written nowhere but the
  test notes. It only ever holds signet coins. Not the BIP-84 "abandon" wallet:
  anyone can spend that, so its coins and history change under the test. That
  one stays for read-only checks.
- Accounts: `84h/1h/0h` (P2WPKH) and `49h/1h/0h` (P2SH-P2WPKH).
- Fund it from a signet faucet, a few coins of different sizes on each account.
- Its public descriptors are in `tests/e1/wallet.mjs`. Its words go nowhere but the
  `E1_WORDS` environment variable of a run.

## Servers

- **signet through blockstream.info** (`https://blockstream.info/signet/api`),
  at the public pace. It's what the live check used; a wallet of about 100
  used addresses took about 2 minutes to scan.
- **Not mempool.space from this machine** for now: it stopped accepting
  connections after the rate measurements. Rate measurements on public servers
  need asking first.
- **Count the total, not just the pace.** Repeated full passes got a 429 from
  blockstream.info too, at the public pace. `tests/e1/harness.mjs` reads each path once,
  through a cache: delete `tests/e1/.cache` only to read afresh.
- The local tunnel was flapping during W1 and W2, which makes Chromium
  fail requests with `ERR_NETWORK_CHANGED`. If a run misbehaves, note the time.

## Part 1: without a camera

Fast, repeatable, nothing moves off the machine but reads. In each direction:

- **Wallet to signer:** the IDE's Camera bar takes a code from text, one per line
  for an animated code (zerogap's `docs/IDE.md`, "The camera"). Copy the PSBT's
  Base43 text, or the series. To get those, read the codes off the page, or
  save the `.psbt` and convert it. Scenarios have `camera qr <text>` and
  `camera qrhex <hex>` (`docs/SIMULATOR.md`).
- **Signer to wallet:** `tools/zgsim --shot` saves the screen as a PNG. Decode it
  with `decodeFrame` (`src/qr.js`) to a file, then "Or open a file" in the page,
  or paste. That is the same decoder the camera path uses.

Each row is one run, on both accounts (`tests/e1/rows.mjs`, results in
`tests/e1/RESULTS.md`):

| Case | Expect |
| --- | --- |
| One input, change, Base43 | The signer shows amount, fee and change as the wallet's review did; change goes from amber "claimed" to green once keys load; the page says "This is the transaction built here". |
| Several inputs, the coins chosen by hand | The same, and "signs 2 of 2 inputs". |
| Send everything | No change output, nothing claimed. |
| Change dropped as dust | The fee is what the page's note says. |
| Series: 2, 8 and 15 codes | The signer joins them, and answers with a series when its answer needs one. |
| Signed code from another transaction | The page refuses to broadcast without the explicit tick. |
| Partly signed PSBT back (a key that signs some inputs) | The page says how many are signed, and offers no broadcast. |
| Wrong master fingerprint on a zpub import | The signer says the keys are from another wallet. The page can't catch this: it's why the first address is compared on import. |

Then the attacks, on PSBTs edited by a script (`tests/e1/attacks.mjs`, results in
`tests/e1/RESULTS.md`), each of which the **signer** must catch; the wallet isn't
involved:

| Edit | Expect |
| --- | --- |
| Change script swapped for another key's, path unchanged | Red: refuted, counted as sent, "Sign anyway". |
| Change moved to an unwatched path | Amber with the path, counted as sent. |
| `PSBT_IN_WITNESS_UTXO` amount lowered | With the previous transaction: refused, they disagree. |

## Part 2: through a camera

The IDE's **Webcam** mode, filming GapWallet on another screen or a phone: the
first test with blur, glare, moiré and frames caught mid-change. The same page
camera reads the simulator's screen for the way back. Then the same on the rig
with the Pi Camera.

These numbers are guesses until measured, and are what this part is for:

| Setting | Now | Find out |
| --- | --- | --- |
| Densest QR version a camera reads reliably | none known | Base43 at versions 13, 20, 25, 30 |
| Series: version | at most 12 | versions 8, 12, 16 |
| Series: time per code | 500 ms | 250, 500, 1000 ms; time to a complete read, and which parts are missed |
| Display size | up to about 620 px | what's needed at what distance |

Record for each: distance, screen, time to a full read, retries. Change
`SERIES_VERSION`, the speed and `LARGE_QR_VERSION` from the results, and give
them on.

## Part 3: for real, on signet

With a go-ahead. One of each account, Base43 and a series (`tests/e1/spend.mjs`, results
in `tests/e1/RESULTS.md`; the simulator's half is done):

1. Build, sign in the simulator, read back, broadcast through the page.
2. The page's txid is the one the server answers with, and the bytes are the ones
   the signer signed (it shows no txid; its log has their SHA-256).
3. Rescan: the coins moved, the change is at the expected index, history shows
   the send once with its fee, and a send to the wallet's own address shows as
   moved within the account.
4. A second spend uses the next change index.
5. After a confirmation, confirmations count up.
6. A broadcast refused (spend the same coin again): the node's error is shown,
   nothing is retried.

Then again with the signer on the rig.

## Part 4: what bitcoind checks

An independent implementation looking at the same bytes. Nothing here spends;
`testmempoolaccept` doesn't broadcast. Nodes to use:

| Node | Good for | Limits |
| --- | --- | --- |

| Call | On | Checks |
| --- | --- | --- |
| `getdescriptorinfo` | The wallet's descriptor | The checksum, and that Core reads it. On v22, expand it first into two: `…/0/*` and `…/1/*`, each with its own checksum (`descriptorChecksum`). |
| `deriveaddresses` | The same, range 0 to 20 | Addresses match `addressAt`, on both chains and both script types. Adds a check beyond BIP-84's and BIP-49's few vectors. |
| `decodepsbt` | Each PSBT | Parses. Fingerprint and path on each input and on the change; `redeem_script` on nested; `non_witness_utxo` **with witnesses stripped**, the one thing core asked to see confirmed here. |
| `analyzepsbt` | The unsigned PSBT | `next` is `signer`; estimated vsize and fee against the page's. |
| `analyzepsbt` | A signed PSBT, if the signer gives one | `next` moves on; the signature is valid. |
| `testmempoolaccept` | The signed transaction, before broadcast | `allowed: true`, with the same fee and vsize the page showed. This is the check that the whole thing is valid by Core's rules, not just ours. Needs the node to know the coins. |

A script (`tools/check_core.mjs`) can run these from a saved `.psbt` and `.txn`,
taking the RPC address and credentials from the environment and never from a
file in this repository. It is written when access exists, and stays out of
`npm test`.

**Regtest** would need bitcoind and electrs, or a shim giving the endpoints in
`docs/ESPLORA.md` on top of bitcoind's RPC. It would allow mining on demand and
no public server. It is only worth it if signet proves too slow or unreliable;
the owner decides.

## Part 5: E2, Electrum

The plan asks for this after E1, with the same wallet:

- Electrum reads our Base43 PSBT, and shows the same transaction.
- A transaction Electrum finished, read back by this page.
- Whether Electrum reads BBQr at all (open in BITCOIN.md); if not, Base43 stays
  the way to Electrum, and the page's two formats already allow it.

## Results

Each run: date and time, commits of both repositories, the case, what happened,
what was not as expected. Passing cases one line each; a failure gets the bytes
that caused it, kept as a test in `tests/` where it can be. No seed in any log,
even this one's: public keys and descriptors only by their length, as
BITCOIN.md asks.
